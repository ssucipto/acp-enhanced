## ADR-10 | 2026-06-15 | Ship M64 (integrity gateway truth/test) before M58 v2.0 semantic analysis

**Status:** Accepted
**Context:** Audit-070 (M55–M58 gateway deep dive) found `/acp-review` (M55) is production-grade, but `/acp-integrity` v1.0 (M56) gives **false assurance**: ~18 of 55 advertised script-backed rules are actually implemented, `acp.entropy-scan.sh` crashes on every positive finding (`set -e` + `exit 3`), the unicode scanner is too slow for practical gating, and `e2e/acp.integrity.test.sh` exercises structure only — not detection. M58 was planned to add Phase 2 semantic rules (taint flow IG-45–50, semantic injection, memory poisoning) on top of this v1 gateway. Route-155 research (taint-flow calibration) is complete, but building v2.0 scanners on an untested, partially-honest v1 foundation would compound user trust in a tool that already prints green while CRITICAL rules never run.
**Options considered:** (1) Proceed with M58 v2.0 in parallel with M64 — faster feature delivery but stacks LLM/heuristic semantic analysis on a broken v1 base; new findings would be unverifiable in CI. (2) Ship M58 v2.0 first, defer M64 — preserves roadmap order but ships more advertised capability atop known false-assurance gaps; increases security liability. (3) **Gate M58 implementation on M64 exit criteria** — harden v1 truth + test coverage first (M64 routes 179–184), then resume M58 routes 156+; M65 route-187 documents the plan correction. (4) Deprecate `/acp-integrity` until rewrite — honest but discards M56 investment and blocks recurring-task hooks.
**Decision:** Option 3. **M64 is a hard prerequisite for M58 v2.0 implementation work.** M58 may continue **research-only** deliverables (route-155 calibration artifact, fixture drafts) that do not ship new enforced rules or change `--ci` behavior. No M58 route that implements taint/memory/semantic-injection detection, updates integrity rule enforcement tables, or expands the v1 scanner surface may start until M64 milestone exit criteria pass: scanners do not crash, documented coverage matches executed coverage, uniform output contract, and per-rule true+/true− fixture matrix with clean-codebase false-positive baseline (per `milestone-64-integrity-gateway-v1.1-truth-and-test.md` §4). `/acp-review` remains the reference design for output quality; it is not blocked.
**Consequences:** `progress.yaml` and M58 milestone notes must state M58 is **blocked on M64** for implementation routes. Recommended execution order: **M59 (critical CI) → M64 → M65 (tracking reconciliation) → M58 route-156+**. M65 route-187 ADR/plan-correction intent is satisfied by this record. Quarterly `quarterly-deep-scan` recurring task (taint/memory rules) stays deferred until M58 ships. Re-opening M58 implementation before M64 exit requires explicit ADR supersession.
**DO NOT re-open** unless M64 exit criteria are met and verified in a post-M64 audit (e.g., audit verifying fixture matrix + entropy/unicode scanners on real findings), OR audit proves v1 gateway is fully honest and tested without M64 (unlikely — would require counter-evidence to audit-070).

## ADR-9 | 2026-06-04 | Dual-store architecture: registry → document sync on commit

**Status:** Accepted
**Context:** ACP Enhanced maintained two separate stores for patterns and sessions — a compact YAML registry (`agent/memory/*.md`) and individual markdown documents (`agent/patterns/*.md`, `agent/sessions/*.md`) — with no automated sync between them. `/acp-commit` only wrote registries. The FIFOZ project discovered this when both the Patterns and Sessions pages in the ACP Visualizer showed empty despite 36 pattern entries and 14 session entries in the registries.
**Options considered:** (1) Single-store: eliminate registries, use only document directories. Simpler but loses compact diffable representation. (2) Single-store: eliminate documents, agents read from registries. Loses human-readable format and breaks visualizer. (3) Dual-store with commit-time auto-sync: registry remains source of truth, documents auto-generated on every `/acp-commit`. Combines benefits of both stores with a single sync trigger.
**Decision:** Option 3 — dual-store with commit-time auto-sync. `/acp-commit` steps 2b/3b auto-generate `agent/sessions/{date}-{slug}.md` and `agent/patterns/{name}.md` from registries on every successful commit. Step 6b handles re-sync after weekly compaction. `--no-sync` provides an escape hatch for debugging. Standalone `/acp-pattern-sync` and `/acp-session-sync` commands serve as repair tools using the same engine. Sync is idempotent — re-running without registry changes does not rewrite files.
**Consequences:** All future `/acp-commit` calls will auto-sync documents by default. Pre-v6.9 projects can use the repair tools to bootstrap their document directories. The dual-store model must be documented in `agent/wiki/architecture.md`. Visualizer must align its schema with commit output fields (`tasks_completed:` not `tasks:`). YAML quoting directives prevent parse failures in registries that would block sync.
**DO NOT re-open** unless a fundamentally different storage model (e.g., SQLite, JSON-based) is proposed as a replacement for YAML registries.

## ADR-8 | 2026-05-05 | Upstream feature parity: do not re-port independently-implemented features

**Status:** Accepted
**Context:** During the upstream integration analysis (v7.2.0 vs ACP Enhanced), a code-level audit revealed that ACP Enhanced independently implemented the majority of upstream's Tier 1 and Tier 2 features — `acp.meta-scan.sh`, `agent/specs/`, `@acp.spec` with FR-IDs and Behavior Tables, DR-IDs in designs, `incorporates:` in tasks, `@acp.validate` Probes 1–3, `@acp.proceed --stacked` + `--yolo` + Step 3.5 audit + drift remediation, the sessions system, the key-file index, and the full clarification workflow. These were developed in parallel, not ported from upstream.
**Options considered:** (1) Re-port all upstream features regardless — ensures exact parity but wastes effort and risks regression on working implementations. (2) Skip features we already have; only adopt upstream changes that add genuinely missing functionality — efficient and safe. (3) Full upstream audit before any porting; document all parity decisions explicitly — produces a durable record for future sync cycles.
**Decision:** Option 3 as process, Option 2 as default rule. Treat our independent implementations as canonical. Do not re-port a feature if we have a working equivalent. Before any future upstream sync, run a code-level audit (not just CHANGELOG reading) to identify what we actually have vs what we assume we're missing. Real gaps confirmed in this analysis: `agent/drafts/` directory missing, E2E tests for meta-scan/spec/sync/drafts system absent, AGENT.md undocumented for markers/specs/DR-IDs/stacked mode/naming convention.
**Consequences:** Future upstream integration work targets only verified gaps. The feature parity matrix (task-155) becomes a required artifact before any upstream porting milestone. Lessons.md updated to warn against assumption-based gap analysis.
**DO NOT re-open** unless upstream introduces a fundamentally new feature category (not just an enhancement to an existing one) that ACP Enhanced has no equivalent for.

## ADR-7 | 2026-05-05 | Upstream integration strategy: selective manual port only — no git merge

**Status:** Accepted
**Context:** ACP Enhanced forked from `prmichaelsen/agent-context-protocol` at v1.0.3 (2026-02-13). Upstream rewrote git history at v6.0.0 (history scrub) — there is no shared commit ancestry between the fork point and upstream's current `mainline`. `git merge upstream/mainline` and `git rebase` are both impossible; they produce conflicts on every single file with no common base to resolve from. Upstream has released v1.0.3 → v7.2.0 (17 minor versions, 30+ patch versions) since the fork. The two codebases have diverged significantly in naming conventions (`@acp.` vs `/acp-`), directory structure (added `agent/memory/`, `agent/routing/`, `agent/skills/`, `agent/wiki/`), and feature set.
**Options considered:** (1) Abandon upstream tracking — simple but risks missing valuable upstream innovations. (2) Attempt git merge/rebase — technically impossible; no shared ancestry. (3) Cherry-pick individual commits — would require translating every commit SHA, and upstream's history rewrite means older commit SHAs no longer exist. (4) Manual selective port — read upstream source files individually, evaluate each feature, manually translate and adapt any worth adopting. Requires naming convention translation (`@acp.foo` → `/acp-foo`, `@acp-foo` never valid).
**Decision:** Option 4 — manual selective port. For each upstream feature: (a) check if ACP Enhanced already has an equivalent via code-level audit, (b) evaluate compatibility with our constraints (macOS BSD bash, no external deps, 5k token budget, `/acp-` naming), (c) port only if genuinely missing and compatible. This is a read-and-adapt operation, never a git operation. Naming translation rule: globally replace `@acp.<name>` → `/acp-<name>` and `@acp-<name>` → `/acp-<name>` in any ported content.
**Consequences:** No upstream CI integration or automated sync possible. Upstream integration is a deliberate, milestone-scoped activity (M29+). The feature parity matrix (task-155) documents every upstream feature and our port/skip/defer decision. Future upstream syncs require repeating this audit process from the upstream CHANGELOG.
**DO NOT re-open** unless upstream introduces a formal compatibility layer or versioned package export that makes automated sync viable.

## ADR-6 | 2026-05-04 | Cross-tool slash command parity via per-tool command directories

**Status:** Accepted
**Context:** ACP slash commands work natively in GitHub Copilot via `.github/prompts/acp-*.prompt.md`. In opencode (and other terminal-based agents), custom commands live in `.opencode/commands/*.md` and are invoked with `/command-name`. Without `.opencode/commands/`, opencode users have no native slash commands — they rely on the AI guessing intent from AGENTS.md context, which is fragile and model-dependent. The `@acp.<command>` notation is also broken in opencode because `@` is opencode's file-reference syntax, not a command invocation. ADR-4 already eliminated `@acp.*` as canonical — this ADR governs how per-tool parity is achieved.
**Options considered:** (1) Single source directory that generates all tool-specific outputs via a build step — clean but adds tooling complexity. (2) Manually maintain separate per-tool directories (`.github/prompts/`, `.opencode/commands/`) with identical content — simple but drift risk. (3) Add a generator script (`acp-bootstrap.sh` step) that creates `.opencode/commands/` from `.github/prompts/` at install time — single source of truth, no build step in CI.
**Decision:** Option 3 — `acp-bootstrap.sh` generates `.opencode/commands/acp-*.md` from `.github/prompts/acp-*.prompt.md` at install time. The `.github/prompts/` directory is the canonical source. The `.opencode/commands/` directory is a derived artifact. Command content for opencode mirrors `.github/prompts/` exactly (same delegation pattern: "Read and execute `agent/commands/acp.*.md`"). Meta-commands (acp-commit, acp-route, acp-decide, acp-cost-report, acp-memory-sync, acp-wiki-update) embed content inline in both directories identically.
**Consequences:** One canonical source (`.github/prompts/`). `acp-bootstrap.sh` and `acp.install.sh` both create `.opencode/commands/` automatically. Any new command added to `.github/prompts/` must also update the bootstrap generator. An E2E test (`acp.opencode-commands.test.sh`) enforces 1:1 parity — no silent drift. Adds `.opencode/` to `.gitignore` is rejected — files must be committed so project clones get opencode support without re-running bootstrap.
**DO NOT re-open** unless a third tool ecosystem (e.g., Cursor, Claude Code) requires its own command directory format, at which point extend this pattern rather than replace it.

## ADR-12 | 2026-06-15 | M58 §10 go/no-go gate: accept literature-derived confidence ceilings, remove circular empirical precondition

**Status:** Accepted
**Context:** The original M58 §10 go/no-go gate for v2.0 was circular: it gated routes 156–158 on empirical taint TPR measurement, but that TPR was planned to be "measured in route-158" — which is itself gated by the §10 decision. A deliverable cannot be its own prerequisite. Audit-069 F-069-04 identified this circularity. Additionally, routes 156–158 are implementation routes for memory poisoning scanners and end-to-end testing, not measurement routes. The intended measurement work was in route-155, which took a literature-calibration approach rather than empirical benchmarking.
**Options considered:** (1) Move empirical TPR measurement into route-155/156 (before the gate) — requires re-opening route-155 and adding measurement routes, adding 1-2 weeks. (2) Accept the literature-derived confidence ceilings explicitly and remove the empirical precondition — non-circular, matches the actual research artifact delivered. The confidence ceiling model (taint ≤ MEDIUM, semantic injection ≤ LOW, memory poisoning ≤ LOW) was already established by ADR-10 and the route-155 research, independent of the circular gate.
**Decision:** Option 2. The §10 gate accepts the literature-derived confidence ceilings as the go/no-go basis. M58 v2.0 implementation proceeds under the confidence ceiling policy: taint-flow findings carry MEDIUM confidence (advisory, never CRITICAL in `--ci`), semantic-injection and memory-poisoning carry LOW confidence (require human review, never auto-fail CI). The circular empirical precondition is removed. Re-opening for empirical benchmarking requires post-ship operational data and a new ADR.
**Consequences:** Milestone §10 updated to a non-circular sequence: research complete → confidence ceilings established → proceed with implementation under ceiling policy. The fixture manifest encodes `max_confidence` and `ci_blocking: false` for all taint-flow rules. Route-158 E2E tests assert no CRITICAL auto-fail on taint fixtures and confidence ≤ MEDIUM.
**DO NOT re-open** unless M58 v2.0 ships and post-deployment audits find systematic false positives at rates that undermine the literature-derived confidence model (e.g., >30% false-positive rate on clean codebase samples).

## ADR-13 | 2026-06-15 | LLM/Script boundary rule for /acp-integrity: deterministic → bash, semantic → LLM

**Status:** Accepted
**Context:** `/acp-integrity` (audit-052, M56) needed a clear division of responsibility between bash scripts and LLM reasoning. Without an explicit boundary, each integrity rule implementation risked either slow LLM-as-deterministic-checker (waste) or bash scripts trying to reason about semantics (impossible). The `code-integrity.md` skill document (shipped with M56) established this boundary de facto; this ADR formalizes it.
**Options considered:** (1) LLM-only — every check runs through the model. Slow, expensive, inconsistent. (2) Bash-only — every check is a deterministic script. Impossible for semantic categories (taint flow, injection, memory poisoning). (3) Boundary rule — bash handles structural/deterministic categories (entropy, unicode, manifest, network, git, dependency), LLM handles semantic/heuristic categories (taint flow, prompt injection, memory poisoning).
**Decision:** Option 3 — the LLM/Script Boundary Rule. Category 1–7 integrity rules (deterministic, structural) run as bash scripts with uniform output contracts. Category 8–10 (semantic, heuristic) invoke LLM reasoning within confidence ceilings. The `code-integrity.md` skill document is the canonical reference. Source: audit-052 architectural finding, `agent/skills/code-integrity.md` (M56).
**Consequences:** Every new integrity rule must declare which side of the boundary it lives on. No hybrid rule that mixes bash + LLM in a single check (complicates output contracts). `/acp-integrity --ci` only runs bash categories (1–7); semantic rules require explicit `--deep` flag or `--rules taint-flow,memory` invocation.
**DO NOT re-open** unless a fundamentally different integrity architecture (e.g., all-script with AST-based semantic analysis) becomes viable and demonstrates better accuracy-per-cost than the LLM/heuristic approach.

## ADR-14 | 2026-06-15 | Confidence ceiling policy for semantic security analysis: MEDIUM (taint) / LOW (injection, memory)

**Status:** Accepted
**Context:** M58 Phase 2 (semantic integrity rules) introduced LLM-reasoned and heuristics-based detection for taint flow, prompt injection, and memory poisoning. These categories cannot match the deterministic accuracy of bash structural checks. Publishing them with the same severity/confidence levels as deterministic rules would create false assurance and could block CI on shaky findings. A confidence ceiling policy was needed to govern how these findings are reported and acted upon.
**Options considered:** (1) No ceiling — report semantic findings with same confidence as deterministic ones. Dangerous — LLM hallucination or heuristic false positives would carry CRITICAL severity and potentially block production CI. (2) Hide semantic findings — only use them for audit logging. Wastes the detection capability; developers never see the warnings. (3) Confidence ceiling — semantic findings are capped at MEDIUM (taint flow) or LOW (injection, memory), are advisory-only (never CI-blocking), and display a confidence tag. This is the pattern established by ADR-10 and ADR-11/12.
**Decision:** Option 3 — confidence ceiling policy. Taint-flow (IG-45–50): MEDIUM confidence, advisory-only in `--ci` (exit 0 even with findings). Semantic injection (IG-53/54/56/57) and memory poisoning (IG-58–62): LOW confidence, `REQUIRES_HUMAN_REVIEW` tag, guaranteed non-blocking in CI. The fixture manifest encodes `max_confidence` and `ci_blocking: false` for all taint-flow rules. No semantic finding carries CRITICAL severity until empirically validated (M70+).
**Consequences:** `/acp-integrity --ci` never fails on semantic findings alone. Developers see them as warnings with explicit confidence tags. The confidence ceiling can be re-evaluated per-category after M70 empirical benchmarking. Source: `agent/wiki/integrity-rules.md` v2.0, `agent/benchmarks/fixtures/taint-flow/manifest.yaml` v1.1.0.
**DO NOT re-open** unless M70 provides empirical false-positive/true-positive rates that justify raising a category ceiling above MEDIUM.

## ADR-15 | 2026-06-15 | Command doc as spec — no separate specification files for ACP commands

**Status:** Accepted
**Context:** Audit-052 found that M55 route-133 created a separate `spec.md` file as a companion to the `code-review.md` skill document. This introduced a maintenance burden: two files to keep in sync, two sources of truth, and drift between them. The decision was made to merge the spec into the skill document — making the command doc itself the specification.
**Options considered:** (1) Separate spec + implementation — traditional software engineering, but creates drift between spec and implementation in a documentation-first project. (2) Command doc as specification — the skill document IS the specification. Acceptance criteria, verification steps, and expected output all live in one file. Simpler, self-validating (the document describes what `/acp-review` does and is itself verifiable by running `/acp-review`). (3) Tests as specification — rely solely on E2E tests. Fragile; tests don't communicate intent to humans.
**Decision:** Option 2 — command doc as spec. Every ACP command and skill document serves as its own specification. No separate `.spec.md` or `.design.md` files are created for commands. Design decisions are captured as inline ADRs or referenced from `agent/memory/decisions.md`. Verification checklists in each command doc serve as acceptance criteria. This is the pattern established by M55 (merge route-133 spec into `code-review.md`) and reinforced across all subsequent milestones.
**Consequences:** Fewer files to maintain. No spec-drift between "what it should do" and "what it documents". Every `/acp-validate` run checks the command doc's internal consistency. The `agent/skills/` directory contains specification-quality documents, not just implementation guides. Source: audit-052 finding, `agent/skills/code-review.md` (M55), `agent/skills/code-integrity.md` (M56).
**DO NOT re-open** unless a regulatory or compliance requirement mandates separate specification documents with formal traceability matrices.

## ADR-16 | 2026-06-15 | Gitflow-lite branching model: develop → mainline (no release branches)

**Status:** Accepted
**Context:** The project needed a branching model that balances clean CI/CD flow with minimal ceremony. Full gitflow (with release branches, hotfix branches, and support branches) was overkill for a 1-developer framework project. Trunk-based development lacks the review gate needed for a project where bugs can corrupt agent behavior. The project adopted `develop → mainline` (gitflow-lite) during M54.
**Options considered:** (1) Full gitflow (main + develop + release + hotfix) — too many branches for a solo project. (2) Trunk-based (everything on main) — no gate before CI-published artifacts; risky for agent-directive code where a bad commit can mislead every agent invocation. (3) Gitflow-lite (develop → mainline) — one working branch, one production branch. Feature/fix branches merge into develop. PRs merge develop → mainline. Two environments: develop (staging) and mainline (production).
**Decision:** Option 3 — gitflow-lite (`develop` → `mainline`). All work happens on `develop` or feature branches. CI runs on every push and PR. `mainline` is the production branch — no direct commits. PRs gate `develop → mainline` merges. Branch protection is enforced on both branches (route-162 / M59). The naming uses `mainline` (not `main` or `master`) to avoid ambiguity with ACP's `main:` context key.
**Consequences:** `agent/core/identity.yml` encodes the `git_workflow` block with `default_working_branch: develop` and `production_branch: mainline`. All ACP protocol files check the current branch before executing write operations (Step 1b of context loading protocol). Source: M54 implementation, `agent/core/identity.yml → git_workflow`, `agent/core/constraints.yml → branch_safety`.
**DO NOT re-open** unless the project grows to 3+ regular contributors requiring release-management branches or an LTS release track.

## ADR-17 | 2026-06-15 | Light/full context modes + 2,800-token budget discipline

**Status:** Accepted
**Context:** ACP Enhanced adopted a tiered context loading model to solve the token-overflow problem that plagued earlier agent frameworks. Without explicit discipline, agents load everything indiscriminately, overflow their context window mid-session, and lose information permanently. The project needed a hard constraint with a documented override path for tasks that genuinely need more context.
**Options considered:** (1) No budget — load all files unconditionally. Causes context overflow, silent session termination, and permanent knowledge loss. (2) Auto-detect limits — try to estimate token usage dynamically. Fragile; token estimation varies by model and serializer. (3) 2,800-token budget with light/full modes — a practice discipline (not a technical limit) that keeps sessions reproducible and cost-controlled. Exceed deliberately when needed and note it.
**Decision:** Option 3 — three-layer model with a 2,800-token soft budget. Layer 1 (core/): max 500 tokens, always loaded, prompt-cacheable. Layer 2 (skills/): max 1,000 tokens, exactly one per task domain. Layer 3 (memory/ + wiki/): max 3,500 tokens, filtered by task_type and relevance. Total session context: max 5,000 tokens before task content. The budget is a discipline practice — reproducibility, focus, and cost at scale — not a technical limit. Exceed deliberately when needed; note it.
**Consequences:** 75–88% token reduction vs monolithic AGENT.md. Prompt caching on Layer 1 gives additional savings. Skills must cover all task domains exhaustively. Every session start runs the Context Loading Protocol (Steps 1–6 in AGENTS.md). Source: `agent/core/constraints.yml`, `agent/core/identity.yml`, `AGENTS.md` Context Budget section.
**DO NOT re-open** unless a task type genuinely requires >5,000 tokens of pre-task context to complete correctly, AND the additional context can't be loaded on-demand via `/acp-init --full`.

## ADR-20 | 2026-06-15 | Hooks are a task_id array referencing recurring_tasks — not booleans

**Status:** Accepted (backfilled 2026-07-23 — the decision shipped in M62 commit 808152c and was cited by `agent/core/constraints.yml` but never written to this file; audit-097/M78 planning surfaced the dangling reference)
**Context:** The `hooks.pre_commit` block in `agent/core/constraints.yml` needed a format. An early conception modeled hooks as booleans (e.g. `unicode_scan: true`, `ignore_scripts: true`) — one flag per behavior. That duplicates behavior already defined as `recurring_tasks` in `progress.yaml` (each with a command, executor, cadence, and `last_findings_count` feedback loop), creating two sources of truth that drift: a boolean says "on" while the underlying task's executor/command/cadence lives elsewhere and can silently diverge. M62 (route-176, audit-062 F-062-01) restored two dropped hooks — `pre-commit-integrity-phase1` (fast unicode+entropy scan) and `ci-npm-ignore-scripts` (npm `--ignore-scripts` supply-chain isolation) — and needed a format that would not lose hooks again.
**Options considered:** (1) Booleans per hook — compact, but a second source of truth that duplicates and drifts from `recurring_tasks`, and carries no executor/description, so it can't be cross-validated. (2) Inline full hook definitions in constraints.yml — self-contained but re-duplicates command/executor/cadence already in `recurring_tasks`, and bloats a Layer-1 core file. (3) **Array of `{ task_id, description }` entries, each `task_id` referencing a `recurring_task` by id** — hooks become pointers into the single `recurring_tasks` registry; executor and command are cross-validated against that registry, and a dropped hook is a broken reference the validator can catch.
**Decision:** Option 3. **`hooks.pre_commit` (and any future hook phase) is a list of `{ task_id, description }` entries; `task_id` MUST resolve to a `recurring_tasks[].id` in `progress.yaml`.** Booleans are prohibited for hooks. `recurring_tasks` remains the single source of truth for what a hook actually runs (command, executor, cadence); the hook entry only says "this task fires at this lifecycle point" plus a human-readable description. This is why `constraints.yml` hook descriptions carry the "(ADR-20: format change from booleans to task_id array)" annotation.
**Consequences:** Adding a hook means (a) the referenced `recurring_task` exists in `progress.yaml`, and (b) a `{ task_id, description }` entry is added under the relevant `hooks.<phase>` key — never a boolean. Validation (acp-validate) can enforce that every hook `task_id` resolves to a real recurring_task and cross-check its executor. The supply-chain hooks restored in M62 (`pre-commit-integrity-phase1`, `ci-npm-ignore-scripts`) stay in this format. This backfilled ADR resolves the two previously-dangling "ADR-20" citations in `constraints.yml`; no code or format change is implied by writing it down — the format was already in force since M62.
**DO NOT re-open** unless the `recurring_tasks` registry is removed (eliminating the referent) or hooks gain per-invocation parameters that a bare `task_id` reference cannot express.

## ADR-23 | 2026-07-27 | Local deterministic analyzers are a separate class from ADR-19 gated cloud integrations

**Status:** Accepted
**Context:** M83 tasks 290, 292, and 293 needed a governance decision that ADR-19/21/22 do not cover. audit-102 and audit-103 surfaced three related gaps: (1) `/acp-review` has clear candidate delegations to local deterministic analyzers such as `shellcheck`, `gitleaks`, and `dupehound`; (2) the existing optional-tool pattern in `agent/patterns/local.optional-external-tool.md` only documents strict opt-in, while the 2026-07-27 maintainer discussion chose auto-enable-on-detection for a narrow no-egress class; and (3) assisted installation needed an explicit boundary so ACP does not drift into direct binary download or toolchain bootstrap. ADR-19 remains a DO-NOT-re-open adoption gate for cloud/vendor integrations whose real output contracts must be learned from live use. ADR-21 and ADR-22 remain the CodeRabbit carve-outs within that cloud-tool family. This ADR defines a separate category for **local, offline, deterministic analyzers** and the constraints under which ACP may detect or help install them.
**Options considered:** (1) Treat local analyzers like CodeRabbit/Aikido and gate them under ADR-19. Rejected: ADR-19 was written for live vendor integrations and speculative output-shaped work, not for local tools whose invocation and output can be verified immediately on the maintainer’s machine. (2) Allow any detected external tool to auto-enable by analogy. Rejected: that would weaken the privacy/consent rationale behind the optionality pattern and could accidentally expand to cloud or mutating tools. (3) Define a distinct local-analyzer class with a narrow detection-as-consent variant and strict install boundaries. Accepted.
**Decision:** Option 3. Three decisions are in force. **First:** `dupehound`, `gitleaks`, and `shellcheck` are treated as **local deterministic analyzers outside the ADR-19 gate** when ACP uses them only as local analyzers; they are offline-verifiable and do not reopen or supersede ADR-19/21/22. **Second:** the optional external-tool pattern now has a **Variant B: detection-as-consent** for tools that pass an explicit eligibility test: the tool must be **offline, read-only on the workspace, and have no network egress in the ACP code path**. Variant B must still honor a mandatory explicit-`false` escape hatch (`integrations.<tool>.enabled: false` disables the tool even when detected). Tools that do not pass all three conditions stay on Variant A (strict opt-in authoritative). **Third:** ACP may offer assisted installation for these tools only with explicit user consent and only through trusted package managers already expected on the host (`brew` or `cargo` for this ADR’s scope). ACP must never download third-party binaries directly, never curl-pipe installers, and never install Rust/toolchains as part of the offer. If `cargo` is absent, ACP may describe the prerequisite but must not bootstrap it.
**Consequences:** M83 may proceed with local-analyzer tasks (`shellcheck`, `gitleaks`, `dupehound`) without claiming a carve-out from ADR-19, provided their ACP integration stays local, read-only, and output-verifiable. `agent/patterns/local.optional-external-tool.md` must document both Variant A and Variant B, including the eligibility test and the explicit-`false` override. Future cloud or vendor-backed integrations remain governed by ADR-19/21/22; this ADR does not loosen CodeRabbit or Aikido gating, does not authorize speculative API/import design, and does not permit direct binary download or language-toolchain installation.
**DO NOT re-open** unless one of these analyzers requires network egress or workspace mutation in normal ACP use, or ACP adopts a new install mechanism that is neither a trusted package manager nor covered by an explicit successor ADR.
